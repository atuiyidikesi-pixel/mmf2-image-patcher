# 实战记录：一个 MMF2 点阵游戏的汉化逆向

> 本文记录一次完整的技术攻关。为避免版权问题，**样例游戏统一称为「样例游戏」**，
> 不提供游戏名、截图与任何素材。所有数字均为实测结果。

---

## 0. 起点：一个不该有编码问题的游戏

样例游戏是一款日文同人横向动作游戏，点阵风格。最初的判断链条是这样的：

1. 引擎是 **Multimedia Fusion 2 / Clickteam Fusion**
   依据：`MMFS2.dll` 导入表、`MMF2Position:` 字符串、若干 MMF×5 / mmf×11 / MMF2×1 标记，
   以及只导入 `KERNEL32/USER32/GDI32/COMCTL32/WINMM/COMDLG32/SHELL32` 的精简导入表。
2. 非 Unicode 的 MMF2 ⇒ 文本按 **ANSI/CP932** 存储
   ⇒ **JIS X 0208 装不下大部分简体字** ⇒ 当时以为汉化会卡在「汉字代用」这种权宜之计上。

**这个前提后来被完全推翻了。**

---

## 1. 工具链：从零编译 CTFAK

现存 MMF2 工具的三个选项：

| 项目 | 语言 | 预编译包 |
|---|---|---|
| CTFAK（原版） | C++ | ✅ 有（0.5-b, 2021） |
| CTFAK 2.0 | C# | ❌ 无 |
| CTFAK-UnEx | C# | ❌ 无 |

先用有预编译包的 0.5-b 试水，它成功解密并解析了数据：

```
Found PackData header!  Found 15 Pack Files
Using New Key
First 16-Bytes of key: 48 DA 89 31 F5 B7 0A 71 72 FF AA 0A C2 B0 27 58
Found Extension: kcini / kcfile / AESFusion / kcwctrl / ctrlx / Joystick2 / AdvDir
```

但随即撞墙：

```
System.Exception: Unsupported movement: 14
   在 CTFAK.MMFParser.EXE.Loaders.Objects.Movement.Read()
```

查 CTFAK 2.0 源码，它的 `Movements.cs` 明确支持 `case 14` —— 于是转向自行编译 2.0。

### 编译过程中修的三个 bug

**① 无控制台时崩溃**

```
System.IO.IOException: 句柄无效。
   at System.ConsolePal.get_WindowWidth()
   at CTFAK.ASCIIArt.DrawArt2()
```

`DrawArt2()` 里的 `var coeff = Console.WindowWidth / Console.WindowHeight;`
在 stdout 被重定向时抛异常——**而这个 `coeff` 赋值后从未被使用**，纯死代码。

**② 静态字段为 null**

自己写工具时第一次加载就崩：

```
System.NullReferenceException
   at CTFAK.CCN.GameData.Read(ByteReader reader)
```

原因：`CTFAKCore.parameters` 与 `CTFAKCore.path` 是**不可为 null 的静态字段**，
解析器无条件解引用（`CTFAKCore.parameters.Contains("-f1.5")`）。CLI 里有初始化，自写工具时漏了。

**③ 运行时版本**

程序声明依赖 `Microsoft.AspNetCore.App 6.0.0`（因为 Core 用了 `Microsoft.NET.Sdk.Web`），
机器上只有 8.x。改 `runtimeconfig.json`：

```json
{ "runtimeOptions": { "frameworks": [
    { "name": "Microsoft.NETCore.App",      "version": "8.0.0" },
    { "name": "Microsoft.AspNetCore.App",   "version": "8.0.0" } ],
  "rollForward": "LatestMajor" } }
```

编译通过后，**游戏被完整解析**：

```
Game Header: PAMU         Fusion Build: 293
Number of frames: 14
Reading Chunk 8755 (Global Strings) / 8742 (Menu) / 13117 (Frame Events) / 26215 (Fonts)
```

## 2. 意外：数据里几乎没有面向玩家的文本

写了一个基于 CTFAK.Core 的提取工具，遍历游戏元数据、全局字符串表、菜单树、
以及每个事件的**全部条件和动作参数**（用反射递归钻进 `Parameter` 的 `Loader` 子对象）。

结果：**3,043 条字符串 / 2,965 条事件参数**，但——

| 类别 | 数量 | 内容 |
|---|---|---|
| 音效文件名 | 绝大多数 | `vo_08-10` `hit72` `bosu32` `crash16_a` `kachi12` |
| 图像资源名 | 大量 | `20_ero_n-01` `eco00_r` `mmf2_sample_step01midd` |
| 限定组 | 少量 | `Group 0/1/3/5/7` |
| **标准 Fusion 应用菜单** | **9 条** | `ファイル` `オプション` `ヘルプ`… |
| **作者内部对象命名** | **约 30 条** | `04_メイン変数` `04_アイテム管理` `04_スペル管理` |

**没有一句对白。**

结论：**游戏的画面文字是预先渲染进图片的**。这直接推翻了第 0 节的前提——
既然文字是像素而不是字符，**Shift-JIS 编码限制根本不适用**，
「汉字代用」这套权宜之计从一开始就用不上。

## 3. 把 23,061 张图变成 310 张

导出全部图像后，按**尺寸分布**筛：

| 尺寸 | 数量 | 判断 |
|---|---|---|
| `132×15` | 2,082 | 宽扁长条 → 疑似文字条 |
| `426×240` | 1,218 | 整屏背景 |
| `5×7` | 1,191 | 微型字模 |
| `426×66` | 205 | 对话框？ |

做接触表目视确认：

- `132×15` = **道具/魔法/菜单标签**（带木质底框 + 金属色文字）
- `426×66` = **完整句子**（委托说明、NPC 对话、道具描述）
- `5×7` / `4×6` = **纯数字字形** `0-9 + - = .`（不需要翻译）
- `200×144` = 角色/敌人**精灵图**（排除）
- `31×7` = `Anime.00` ~ `Anime.12`，**ASCII 调试标签**（不需要翻译）

### 去重是决定性的

```
132×15    总 2,082  →  唯一  153   (93% 是重复)
426×66    总   205  →  唯一  128
80×16     总   180  →  唯一   16
31×7      总   210  →  唯一   13
──────────────────────────────────
          总 2,677  →  唯一  310
```

**需要翻译的不是 2,677 张，而是 310 张。** 同一句 `エナジートニック` 在商店、背包、
状态栏各处复用，去重后只算一张。

## 4. 第一次改写：黑屏

拿最小的改动试水——把一张 `80×16` 按钮的日文换成中文，写回 exe。

**进程活着、窗口正常、画面全黑。**

接下来是一轮代价不小的排查。

### 二分定位

先做两组对照实验，把「拼接逻辑」和「压缩逻辑」排除掉：

| 实验 | 做法 | 结果 |
|---|---|---|
| A | 逐字节复制重建 ImageBank | `sha256` **与原版完全一致** → 拼接逻辑无误 |
| B | 不改进像素，仅重新压缩 | **7,136 条记录全部字节相同** → `zlib.compress(level 9)` 与原压缩器一致 |

两个产出都与原版一模一样，说明**问题只可能出在改动的像素本身**。

同时发现一个反直觉的事实：**图片头里的 `Checksum` 字段，游戏运行时不校验**。
暴力试了 11 种哈希算法 × 6 种数据范围全部对不上（它甚至不是 CRC32），
但改像素后游戏照常运行——省掉了一整个逆向哈希算法的难关。

### 真正的分界

再做一组能区分「填充方式」的对照：

| 变体 | 做法 | 结果 |
|---|---|---|
| C | 改图后让后续 chunk **平移**，文件末尾补零恢复总大小 | ❌ 全黑 |
| D | 改图后**原位替换**，用零填充把 zlib 流补回原长度 | ✅ **完美渲染** |

结论浮出水面：**chunk 偏移必须固定不变**。
（顺便：`zlib` 解压到 `ZLIB_STREAM_END` 即停止，流尾部的填充会被忽略。）

### 找到那张表

在 CTFAK 的日志里注意到一行不起眼的东西：

```
Reading Chunk 21845 (Image Handles)
```

把它 dump 出来——**29,024 字节，最大值 32,957,675 ≈ 图像库大小 32,959,152**，
7,136 张图 ≈ 7,256 个 `int32`。

> **这是一张逐图偏移表。运行时靠它定位图像；CTFAK 这类解析器是顺序读取的，
> 所以解析没问题——但任何一张图的尺寸变化都会让表失效。**

于是得到硬性规则：

> **每张图的 `CompressedSize` 必须与原值完全一致。**

放不下的图，**逐级量化调色板**（128 → 96 → … → 8 色）重新压缩，直到塞进原字节数。

## 5. 四个隐蔽的坑

### 坑 1：Handle 有一个「减一」

```csharp
Handle = reader.ReadInt32();
if (Settings.Build >= 284) Handle--;      // 样例游戏 build = 293
```

磁盘上的 handle 比逻辑 handle **大 1**。按原始值索引，每张图都会错位到相邻槽位——
**而相邻图往往尺寸相同，尺寸校验根本拦不住**。

这个 bug 让前一版「成功替换 140 张」的结果全部写错了位置，
**而字节级验证也发现不了**（验证只检查「我的图在不在 exe 里」，不检查在哪张上）。

修正偏移后才真正对上。

### 坑 2：像素布局不是 `W×H×4`

`DataSize = 112,596`，而 `426×66×4 = 112,464`，差 132 字节。

用**实测反推**：写几种候选布局去还原 CTFAK 导出的参考图，看谁能做到零差异。

```
BGR 平面紧凑（stride = W*3） + alpha 平面按 4 字节对齐（stride = align4(W)）
426*66*3 = 84,348  +  align4(426)*66 = 428*66 = 28,248  =  112,596  ✓
```

六张测试图 **RGB 差 0.00、alpha 差 0.00**。

### 坑 3：文字框的背景是透明的

`426×66` 的「对话框」看起来有深色背景——那其实是合成预览的底色。
真实数据里 **alpha=0 占 82~95%，不透明像素本身就是文字**（白字 + 棕描边）。

第一版按「从背景色里抠字再填回去」的思路做，**完全没有擦除效果**。
正确做法是**重建一张透明画布**，重画中文。

顺带从原图采样填充色与描边色，所以红色警示文本（如「持有金不足」）也保留了红色。

### 坑 4：描边把笔画吃掉了

12px 点阵字体很多是**单像素笔画**。八方向 1px 描边会把细笔画整个盖住，看起来发糊。
改成**单向右下阴影**后立刻清晰。

## 7. 方法总结

这次攻关可复用的部分，不止是代码：

1. **先证伪前提**。原以为要打编码战，结果是图片——如果不先做文本提取，会在错误方向上耗很久。
2. **对照实验 > 猜测**。黑屏时先做「逐字节复制重建」确认拼接无误，再做「只重压缩」确认压缩器一致，
   把搜索空间从三个变量收敛到一个。
3. **区分「能解析」和「能运行」**。CTFAK 顺序读取一切正常，运行时却靠偏移表——
   解析器能读不等于运行时不依赖布局。
4. **字节级回归，而不是「没崩就行」**。而且要知道验证的盲区：它能证明「图在 exe 里」，
   证明不了「图在对的槽位上」——handle 减一那个 bug 就是这么漏过去的。
5. **格式文档比代码更值钱**。代码只对一个游戏有效，格式规格对整类游戏有效。
